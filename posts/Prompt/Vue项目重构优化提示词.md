## 前言

这篇文章分享一套我自己在 Vue 项目里反复打磨的提示词。它不是用来“炫技重构”，而是用来做一件更务实的事：

在**不改变业务行为**的前提下，把项目从“能跑”推进到“可维护、可协作、可扩展”。

如果你经常遇到下面这些问题，这套提示词会很有用：

- 页面目录和路由不一致，新人难定位代码
- `index.vue` 里逻辑、样式、请求、类型全部混在一起
- 样式硬编码严重，主题变量体系失控
- 重构方案看起来很优雅，但上线风险高、回退困难

---

## 这套提示词解决什么问题

我把它定义为：**前端工程化治理提示词**，不是单纯的“代码优化提示词”。

它强制 AI 按这条价值观做决策：

> 删除 > 合并 > 收敛 > 约定 > 抽象

这条顺序非常关键。很多项目不是“抽象不够”，而是“抽象过早、抽象过度”。
先减复杂度，再谈设计质量，才是大多数业务项目的正确路径。

## 我常用的完整提示词

```text
你是一名前端系统架构师（Vue）与工程化治理专家。
在完全不改变任何业务功能、交互、样式表现和对外行为的前提下，对我提供的项目进行系统性结构重构与优化。

价值观：删除 > 合并 > 收敛 > 约定 > 抽象
禁止：为“优雅”引入复杂设计；为未来假设做过度抽象。

⸻

一、目录与模块结构（强约束）
  • 页面目录与路由一致：src/pages/<routeName>/
  • 页面目录固定：
  • index.vue（仅页面级管理）
  • style.scss（仅页面级样式）
  • utils.ts（页面复用逻辑，可选）
  • types.ts（页面类型，可选）
  • 子模块目录（按功能拆分）：
  • index.vue（模块实现）
  • style.scss（模块样式）
  • utils.ts（模块复杂/复用逻辑，可选）
  • types.ts（模块类型，可选）

⸻

二、职责边界（强约束）
  • 页面 index.vue：只允许布局、模块组合、模块通信、共享数据编排；禁止业务实现/复杂逻辑/模块级样式
  • 模块 index.vue：只负责自身 UI 与交互；复杂逻辑 → 同级 utils.ts；类型 → 同级 types.ts
  • 样式：全部放同级 style.scss；页面样式不得侵入模块，模块样式不得外溢

⸻

三、样式与主题体系（强约束）
  • 全局主题变量统一：src/styles/theme/（仅 CSS 变量文件）
  • 按语义拆分变量文件（颜色/间距/边框等）
  • 页面/模块 style.scss：
  • 必须引用所需主题变量
  • 禁止硬编码设计基准值
  • 禁止私建/变相主题变量
  • 发现硬编码样式：仅在具备跨页面价值时才提升为主题变量

⸻

四、重构原则（红线）
  • 分层：页面 → 模块 → 逻辑 → 类型
  • 优先拆分而非堆叠；避免跨模块耦合；不引入无关抽象
  • 所有改动必须：可解释、可回退、可验证
  • 绝不改变任何行为（功能/交互/样式/对外接口）

⸻

五、工作流程（强制）

1️⃣ 问题地图（先诊断）
按 5 类输出：工程化 / 配置 / 架构与模块 / JS·TS / CSS
每条必须包含：不清晰点 + 长期成本原因 + 是否结构性问题

2️⃣ 优化路线图（再规划）
分 P0/P1/P2，每项必须写：范围 / 风险 / 回退 / 行为一致性验证方式

3️⃣ 逐项落地（模板交付）
每个优化项必须输出：
  • 问题 / 方案（明确不做什么）/ 收益 / 风险 / 回退 / 验证
必要时给目录 Before/After 与等价迁移说明

⸻

六、交付与检测（强制）
完成重构后必须执行项目现有的检测命令以确保：
  • 无异常、无 warning（包括但不限于 lint / typecheck / test / build）
  • 若出现任何 error/warning：必须定位原因并修复，直到全部清零
  • 输出：执行过的命令清单 + 结果摘要 + 对应修复点（简要）
```

## 怎么用这套提示词（实操版）

我建议按这 4 步使用，效果最稳定：

1. **先给上下文再给提示词**
   - 项目目录结构
   - 当前页面或模块代码
   - 现有 lint / test / build 命令

2. **明确“行为不变”的判定基线**
   - 哪些是不能变的：功能、交互、接口、视觉
   - 哪些可以变：目录、拆分方式、类型组织、样式落位

3. **要求先诊断再改代码**
   - 先输出问题地图和路线图
   - 你确认后再逐项落地

4. **每次改造后立刻检测**
   - lint、typecheck、test、build 全跑
   - 出现 warning 也要清零，不留“技术债尾巴”

---

## 这套提示词的边界

为了避免误用，我会在团队里反复强调 3 条边界：

- 它不负责“凭空发明架构”，而是对现有项目做**低风险治理**
- 它不追求一步到位，而是追求**可回退的渐进式改造**
- 它不鼓励过度抽象，只有在复用价值明确时才抽象

换句话说，这套提示词不是让 AI 做“重写者”，而是让它做“结构化整理者”。

---

## 我为什么推荐它

我推荐这套提示词，不是因为它“高级”，而是因为它在真实项目里有三点很实用：

- **沟通成本低**：团队对改造范围、风险和回退方案有共同语言
- **协作冲突少**：页面与模块职责清晰，减少互相踩边界
- **结果可复盘**：每一项都有问题、方案、验证、回退，便于复查和复用

如果你也在做 Vue 项目治理，可以直接复制上面的提示词作为基础版，再按你团队规范补充细节。

## 结语

好的重构不是“改得多漂亮”，而是“改完以后更稳定、更容易继续迭代”。

这套提示词的价值就在这里：
**把复杂的重构过程，变成可执行、可验证、可沉淀的方法。**
