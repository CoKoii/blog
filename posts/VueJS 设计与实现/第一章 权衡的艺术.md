## 前言

「框架设计里到处都体现了权衡的艺术」

## 命令式和声明式

<a href="https://chat.baidu.com/search?word=%E8%A7%86%E5%9B%BE%E5%B1%82%E6%A1%86%E6%9E%B6%E6%98%AF%E4%BB%80%E4%B9%88" target="_blank" rel="noopener">视图层框架</a>
通常分为 `命令式` 和 `声明式`,它们各有优缺点

在设计框架时，应该对两种范式都有足够的认知，这样才能做出正确的选择，将两者的优点捏合🤌

### `命令式`

命令式框架的一大特点就是**关注过程**

例如，我们把下面这段话翻译成对应的代码:

```js
获取 id 为 app 的 div 标签
它的文本内容为 hello world
为其绑定点击事件
当点击时弹出提示：ok
```

对应的代码为:

```js
const div = document.querySelector('#app')
div.innerText = 'hello world'
div.addEventListener('click', () => {
  alert('ok')
})
```

### `声明式`

与命令式不同，声明式框架更加**关注结果**

```vue
<div @click="() => alert('ok')">Hello world</div>
```

可以看到，我们提供的是一个「结果」，至于这个结果如何实现，我们并不关心。实现该「结果」的过程，是由 Vue.js 帮我们完成

换句话说，Vue.js 帮我们封装了过程，Vue.js 的内部一定是命令式的，而暴露给用户的却更加声明式

## 性能与可维护性的权衡

命令式和声明式各有优缺点，在框架设计方面，则体现在性能和可维护之间的权衡

**`声明式代码的性能` ≤ `命令式代码的性能`**

假设我们要将上面 div 的文本内容修改为 hello vue3

命令式代码需要这么做：

```js
div.textContent = 'hello vue3'
```

而声明式：

```vue
<!-- 修改前 -->
<div @click="() => alert('ok')">Hello world</div>

<!-- 修改后 -->
<div @click="() => alert('ok')">Hello vue3</div>
```

对于框架来说，为了实现最优的更新性能，它需要找到前后的差异并只更新变化的地方，最终完成这次更新的代码依然是:

```js
div.textContent = 'hello vue3'
```

如果我们把直接修改的性能消耗定义为 A，把找出差异的性能消耗定义为 B，那么有：

- 命令式代码的更新性能消耗 = `A`
- 声明式代码的更新性能消耗 = `A + B`

最理想的情况是，当找出差异的性能消耗为 0 时，声明式代码与命令式代码的性能相同，但是无法超越，Vue.js 选择 `声明式` 的设计方案原因在于**声明式代码的可维护性更强**

在采用 `命令式` 开发代码的时候，我们需要维护实现目标的整个过程，包括手动完成 DOM 的创建、更新
删除等工作，而 `声明式` 代码展示的就是我们要的结果

这就体现了在框架设计上要做出的关于可维护性与性能之间的权衡

> 框架设计者要做的就是：在保持可维护性的同时让性能损失最小化

## 虚拟 DOM

上面说到，**声明式代码的更新性能消耗 = 找出差异的性能消耗 + 直接修改的性能消耗**

如果能够最小号找出差异的性能消耗，就可以让声明式代码的性能无线接近命令式代码的性能

虚拟 DOM 就是为了 `最小化` 找出差异这一步的性能消耗而出现的

使用 innerHTML 操作页面和虚拟 DOM 相比性能如何？

对于 innerHTML 来说，为了创建页面，我们需要构造一段 HTML 字符串

```js
const html = `<div><span>...</span></div>`
```

接着将该字符串赋值给 DOM 元素的 innerHTML 属性

```js
div.innerHTML = html
```

为了渲染出页面，浏览器要把字符串解析成 DOM 树，这是一个 DOM 层的计算，涉及 DOM 的运算远比 JavaScript 层面的计算性能差

我们可以用一个公式来表达通过 innerHTML 创建页面的性能:

**HTML 字符串拼接的计算量 + innerHTML 的 DOM 计算量**

虚拟 DOM 创建页面的过程分为两步：

- 创建 JavaScript 对象，这个对象可以理解为真实 DOM 的描述
- 递归地遍历虚拟 DOM 树并创建真实 DOM

如果只看创建页面时的性能，虚拟 DOM 相比 innerHTML 没有优势可言，细究的话甚至性能更差

接下来看看它们在更新页面时的性能：

使用 innerHTML 更新页面的过程是重新构建 HTML 字符串，再重新设置 DOM 元素的 innerHTML 属性，而重新设置 innerHTML 属性就等价于销毁所有旧的 DOM 元素，再全量创建新的 DOM 元素

再来看虚拟 DOM 是如何更新页面的：

它需要重新创建 JavaScript 对象，然后比较旧虚拟 DOM，找到变化的元素并更新它

这时虚拟 DOM 的优势就体现出来了

**总结：**

innerHTML < 虚拟 DOM < 原生 JavaScript

虚拟 DOM 的性能虽然比不上原生 JavaScript 去操控页面元素，但是可维护性高

不妨思考一下，有没有办法做到，即声明式地描述 UI，又具备原生 JavaScript 的性能呢？

## 运行时和编译时

当设计一个框架时，我们有三种选择：

- 纯运行时的
- 运行时 + 编译时
- 纯编译时

### 纯运行时

假设我们设计了一个框架，它提供了一个 Render 函数，用户可以为该函数提供一个树形结构的数据对象，然后 Render 函数会根据该对象递归地将数据渲染成 DOM 元素

```js
const obj = {
  tag: 'div',
  children: [
    {
      tag: 'span',
      children: 'hello world',
    },
  ],
}
```

tag 代表元素标签名称，children 既可以是一个数组 (子节点)，也可以直接是一段文本

接着，我们来实现 Render 函数

```js
const render = (obj, root) => {
  const el = document.createElement(obj.tag)
  if (typeof obj.children === 'string') {
    el.textContent = obj.children
  } else if (Array.isArray(obj.children)) {
    obj.children.forEach((child) => {
      render(child, el)
    })
  }
  root.appendChild(el)
}
```

```js
render(obj, document.body)
```

运行之后，我们就可以在浏览器中得到如下效果：

```html
<div><span>hello world</span></div>
```

不需要任何编译，直接运行代码就能看到结果，但是手写树型结果的数据对象太麻烦了，而且不直观，能不能支持用类似于 HTML 标签的方式描述树型结构的数据对象呢？

### 运行时 + 编译时

我们可以引入编译的手段将下面的 HTML 结构转变为树形结构

```html
<div><span>hello world</span></div>
```

```js
const obj = {
  tag: 'div',
  children: [
    {
      tag: 'span',
      children: 'hello world',
    },
  ],
}
```

为此，你编写了一个叫做 Compiler 的程序，它的作用就是把 HTML 字符串编译成树型结构的数据对象

```js
// 待编译的 HTML 字符串
const html = `<div><span>hello world</span></div>`

// 调用 Compiler 编译后得到的树型结构数据对象
const obj = Compiler(html)

// 调用 Render 进行渲染
render(obj, document.body)
```

此时我们的框架就变成了一个 `运行时` + `编译时` 的框架

既然编译器可以把 HTML 字符串编译成数据对象，那么能不能直接编译成命令式代码呢？

### 纯编译时

```html
<div><span>hello world</span></div>
```

```js
const div = document.createElement('div')
const span = document.createElement('span')
span.textContent = 'hello world'
div.appendChild(span)
document.body.appendChild(div)
```

这样就变成了一个纯编译时的框架了

## 总结

- 声明式和命令式

命令式更加关注过程，而声明式更加关注结果。命令式在理论上可以做到极致优化，但是用户要承担巨大的心智负担；而声明式能够有效减轻用户的心智负担，但是性能上有一定的牺牲

- 虚拟 DOM

声明式的更新性能消耗 = 找出差异的性能消耗 + 直接修改的性能消耗，虚拟 DOM 的意义就是最小化找出差异的性能消耗，从而让声明式代码的性能无限接近命令式代码的性能

- 纯运行时：用户直接编写可执行的描述代码，浏览器运行时由框架负责解释、计算并渲染 UI。优点是灵活、无需编译；缺点是运行时开销通常更大，性能优化空间相对有限。
- 运行时 + 编译时：用户编写模板或声明式代码，先经过编译转换为更适合执行的形式 (如 render 函数)，再交给运行时框架完成渲染和更新。优点是在灵活性、开发体验和性能之间取得平衡；缺点是仍然依赖运行时，存在一定额外开销。
- 纯编译时：用户编写模板或声明式代码，在编译阶段直接转换为接近底层 DOM 操作的命令式代码，运行时几乎不需要额外框架参与。优点是运行时开销更小、性能潜力更高；缺点是对动态场景支持往往更受约束，编译器实现也更复杂。
